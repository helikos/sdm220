# sdm220 — счётчик электроэнергии в MQTT

Прошивка для ESP32: опрашивает электросчётчик по Modbus RTU (RS485) и
публикует показания в MQTT. Поддерживаются два устройства — **Eastron SDM220**
и **PZEM-004T**; какое собирается, выбирается окружением PlatformIO.

---

## Сборка и прошивка

```bash
cp src/security.h.example src/security.h   # обязательно: впишите SSID и брокера
pio run                  # = pio run -e sdm220 (окружение по умолчанию)
pio run -e pzem
pio run -e sdm220 -t upload
```

`src/security.h` в `.gitignore`, поэтому без первого шага свежий клон не
соберётся. Значения оттуда вкомпилируются в прошивку и видны в `firmware.bin`
через `strings` — собранный бинарник третьим лицам отдавать не стоит.

### Таблица разделов

В `platformio.ini` стоит `board_build.partitions = min_spiffs.csv` —
1.9 МБ на раздел приложения вместо 1.25 МБ у `default.csv`.

**Таблица разделов не обновляется по OTA.** Чтобы 1.9 МБ появились, плату
нужно один раз прошить по USB. До этого прошивка работает в старом разделе —
она туда влезает (≈900 КБ из 1.25 МБ). Но помните: проверка размера при
сборке считает от 1.9 МБ, так что прошивка больше 1.25 МБ соберётся
успешно, а OTA её отклонит.

Если USB трогать не хочется — уберите эту строку, запас на `default.csv`
всё равно комфортный (≈68%).

### Фоллбэки сети

Лестница в пределах одного сеанса, ведётся из `WiFiContext::supervise()`
раз в секунду:

1. **статический IP** — как настроено;
2. **DHCP** — если адрес получен, но брокер недостижим дольше
   `wifiStaticIpGraceMs` (2 мин). Типичный случай: роутер сменил подсеть —
   ассоциация проходит, а маршрута нет. Переключение не требует
   реассоциации: нулевой адрес в `WiFi.config()` поднимает DHCP-клиент
   на живом соединении;
3. тот же порог по числу неудачных **ассоциаций** (`wifiMaxAttemptsPerMode`,
   5) чередует статический IP и DHCP — это покрывает и обратный случай,
   выключенный DHCP-сервер на роутере;
4. **спасательная точка доступа** — если адреса нет вообще дольше
   `wifiRescueApAfterMs` (5 мин). SSID = device id (`sdm220-a1b2c3`),
   пароль `wifiRescueApPass`, адрес 192.168.4.1.

Точка доступа — это **канал для OTA, а не портал настройки**: сохранять
введённые параметры некуда, пока в прошивке нет NVS. Сценарий такой:
сменился SSID роутера → через 5 минут плата поднимает свою сеть → вы
заходите на `http://192.168.4.1/update` и заливаете сборку с новыми
параметрами, не доставая кабель.

Режим — `WIFI_AP_STA`, поэтому station продолжает попытки, и точка
свернётся сама, как только домашняя сеть вернётся.

Выбранный режим **не сохраняется между перезагрузками**: после ребута
отсчёт начинается заново со статического IP.

Пока точка доступа поднята, перезагрузка по таймауту MQTT подавлена —
иначе ребут выбил бы единственный путь к `/update`. Поэтому в `loop()`
порядок вызовов важен: сначала `wifiContext.supervise()`, потом
`mqttContext.supervise()`.

| Набор | Регистры | Период |
|---|---|---|
| SDM220 power | 0, 42 шт. | 1 с |
| SDM220 energy | 70, 12 шт. | 2 мин |
| SDM220 total | 342, 8 шт. | 3 мин |
| PZEM всё | 0, 10 шт. | 2 с |

Таймеры одноразовые и перезапускаются после ответа, ошибки или отказа
очереди eModbus — то есть период считается от момента обработки, а не
от момента запроса.

## MQTT

QoS 1, `retain` включён для всех публикаций.
Client ID — `<устройство>-<3 байта MAC>`, например `sdm220-a1b2c3`:
стабилен для платы и уникален между платами.

### Топики

| Топик | Когда |
|---|---|
| `powermetter/sdm200/power` | напряжение, ток, мощности, cos φ, угол |
| `powermetter/sdm200/energy` | частота, импорт/экспорт активной и реактивной |
| `powermetter/sdm200/total` | суммарная активная и реактивная энергия |
| `powermetter/sdm200/error` | ошибка Modbus |
| `powermetter/sdm200/availability` | `online` / `offline` |

Для PZEM — `powermetter/pzem/{power,error,availability}`.

> Префикс `sdm200` — опечатка, которая тянется с самого начала. Исправлять
> её означает ломать настроенные подписки в Home Assistant, поэтому топики
> оставлены как есть. Менять — в `deviceConfig.cpp`.

### Payload

```json
{"lineVolts":230.1,"current":1.42,"activePower":327.5,"apparentPower":330.1,
 "reactivePower":42.3,"powerFactor":0.95,"phaseAngle":-0.33}
```

### Availability

`offline` публикует **сам брокер** по Last Will — когда устройство пропало,
не прислав DISCONNECT: обрыв WiFi, пропадание питания, `ESP.restart()`.
`online` публикует устройство при каждом подключении.

Брокер объявляет клиента мёртвым примерно через `keepAlive × 1.5`, то есть
около **22 секунд** при `mqttKeepAliveSeconds = 15`. Это не мгновенно —
свойство MQTT, а не этой прошивки.

Для Home Assistant:

```yaml
mqtt:
  sensor:
    - name: "SDM220 активная мощность"
      state_topic: "powermetter/sdm200/power"
      availability_topic: "powermetter/sdm200/availability"
      payload_available: "online"
      payload_not_available: "offline"
      value_template: "{{ value_json.activePower }}"
      unit_of_measurement: "W"
      device_class: power
      state_class: measurement
```

## Когда публикуются показания

Это главная неочевидная часть. Публикация происходит, если выполнено
**хотя бы одно** условие:

1. **первая успешная публикация** — после старта или реконнекта;
2. **истёк heartbeat** — `heartbeatMs`, по умолчанию 20 с, даже если
   показания не изменились;
3. **сменилась epoch подключения** — был реконнект, брокер наполняется
   заново, не дожидаясь heartbeat;
4. **значение вышло за мёртвую зону** относительно последнего
   **опубликованного** значения.

Мёртвая зона: `|Δ| ≥ max(абсолютный порог, deadbandRelPercent % от
предыдущего)`. Абсолютный порог задаёт пол чувствительности около нуля.

Сравнение идёт с последним **опубликованным**, а не прочитанным значением —
иначе медленный дрейф внутри мёртвой зоны не публиковался бы никогда.

Состояние «опубликовано» фиксируется **только после успешной отправки**.
Если брокер недоступен, ничего не фиксируется и следующий опрос повторит
попытку. Буфера в памяти нет: для retained-телеметрии «последнее значение
побеждает», а после реконнекта всё переотправляется по п. 3.

## Настройки

### `src/configuration.h` — общее

| | |
|---|---|
| `debug`, `debug_mqtt`, `debug_processing`, `debug_initialization`, `modbus_Processing` | области логирования |
| `isPrint2Serial` | дублировать лог в Serial (115200) |
| `sizeOfLog`, `msgLength` | кольцевой буфер лога: 128 × 256 байт в `.bss` |
| `heartbeatMs` и `heartbeatMs{Power,Energy,Total,Pzem}` | 20000 мс; `0` = публиковать только по изменению |
| `deadbandRelPercent` | 3.0 % |
| `deadbandVolts / Amps / Watts / Va / Var / PowerFactor / Degrees / Hz / Kwh / Kvarh` | абсолютные пороги |
| `mqttQos`, `mqttRetain` | 1, `true` |
| `mqttKeepAliveSeconds` | 15 |
| `mqttMaxOfflineMs` | 600000 мс; `0` = не перезагружаться |
| `network*` | статический IP, кроме последнего октета |
| `wifiMaxAttemptsPerMode` | 5 неудачных ассоциаций до смены режима IP; `0` = не менять |
| `wifiStaticIpGraceMs` | 120000 мс без брокера на статическом IP до перехода на DHCP; `0` = не переходить |
| `wifiRescueApAfterMs` | 300000 мс без адреса до подъёма точки доступа; `0` = не поднимать |
| `wifiRescueApPass` | пароль точки; короче 8 символов — сеть открытая |

Для energy и total heartbeat 20 с меньше периода опроса (2 и 3 мин),
поэтому на практике они публикуются **на каждом опросе**. Это осознанно:
счётчики энергии монотонны.

### `src/deviceConfig.{h,cpp}` — различия устройств

Имя, последний октет IP, скорость порта, Modbus ID, RS485 RTS-пин, топики.
Всё в одной структуре на устройство.

## HTTP

| | |
|---|---|
| `/log` | кольцевой буфер лога, chunked-ответом |
| `/memory` | свободная куча и `getMaxAllocHeap` |
| `/update` | OTA (AsyncElegantOTA) |

**Аутентификации нет ни на одном из них** — осознанное решение для
устройства в домашней сети. Любой в той же сети может залить произвольную
прошивку. Закрывается одной строкой:
`AsyncElegantOTA.begin(&server, "user", "pass")`.

## Структура

```
src/
  main.cpp              сборка зависимостей, setup/loop, веб-сервер
  configuration.h       общие настройки
  deviceConfig.{h,cpp}  различия между устройствами
  security.h            SSID / брокер (в .gitignore)
  utils/
    IPublisher.h        интерфейс публикации
    MqttContext.*       MQTT: подключение, LWT, реконнект, supervise
    WiFiContext.*       WiFi: статический IP, события, реконнект
    Logger.*            кольцевой буфер лога под мьютексом
    Log.h               макросы LOG / LOG_MQTT / LOG_PROC / LOG_INIT / LOG_MODBUS
    commonFunctions.*   мёртвая зона, /memory
  processing/
    ModbusMqqtProcessing.*  общая часть: Modbus-клиент, запросы, ошибки
    SDM220Processing.*      три набора регистров таблицей каналов
    PzemProcessing.*        один набор
    PublishGate.*           решение «публиковать или нет»
  registers/
    sdm220/   декодирование ответов SDM220 → JSON
    pzem/     то же для PZEM
```

Зависимости передаются по ссылке через `IPublisher`. Колбэки библиотек
привязаны лямбдами с захватом `this`; статические функции остались только
трамплинами для C-колбэков таймеров FreeRTOS, экземпляр передаётся через
timer ID.

### Таски

Код исполняется в четырёх контекстах, это важно при любых правках:

| Таск | Что в нём |
|---|---|
| eModbus | `onData` / `onError` → декодирование и публикация |
| AsyncTCP | колбэки MQTT, обработчики HTTP |
| служба таймеров FreeRTOS | опрос счётчика, реконнекты WiFi и MQTT |
| события Arduino | события WiFi |
| `loop()` | `supervise()` раз в секунду |

`Logger` защищён мьютексом. В колбэках таймеров **нельзя** вызывать
`delay()` — таск службы таймеров один на все таймеры проекта.

## Известные ограничения

- Конфигурация задаётся на этапе компиляции, NVS-провижининга нет. Фоллбэки
  на DHCP и на спасательную точку доступа есть, но выбранный режим не
  переживает перезагрузку, а точка доступа не принимает настройки — только
  даёт добраться до `/update`.
- `AsyncMqttClient` заброшена. Замена — `esp-mqtt` из IDF или `PubSubClient`
  в выделенном таске.
- У power запрашивается 42 регистра, хотя у SDM220 определены 0x0000–0x0025,
  то есть 38. Часть прошивок отвечает на это ILLEGAL_DATA_ADDRESS.
- `debug` включён всегда, выключателя для релизной сборки нет.
- Нейминг: `mqqt` вместо `mqtt` (включая имена файлов), `initializate`
  вместо `initialize`, топики `sdm200` вместо `sdm220`.

Точка доступа — канал для OTA, а не портал настройки: сохранять введённые параметры некуда, пока нет NVS. Сценарий: сменился SSID → через 5 минут плата поднимает свою сеть → заходите на http://192.168.4.1/update и заливаете сборку с новыми параметрами, не доставая кабель. Режим WIFI_AP_STA, поэтому station продолжает попытки и точка свернётся сама, когда домашняя сеть вернётся.
